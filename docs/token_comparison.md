# 字段方案与逐条语义理解：输入token比较

比较以筛选和质量清洗后保留的14,812,812条记录为固定范围，按用户指定的两路输入计量：

```text
C = 1,347个map单元 + 408个entity_only单元的文件卡片方案请求输入token
S = 382个row_llm单元 + 475个review后备单元的完整记录逐条输入token
A = 全部14,812,812条保留记录逐条输入token
混合方案占比 q = (C + S) / A
相应输入量减少比例 = 1 - q
```

这里的475个单元计入复杂语义通道的配置范围。统计它们的输入大小，并不将既有REVIEW结果改写成已经提取的事实。历史记录、事件与画像汇总保持独立口径。

## 本批结果

| 输入部分 | 输入token |
| --- | ---: |
| C：1,347＋408个单元的文件卡片 | 6,877,720 |
| S：382＋475个单元的完整记录 | 3,781,513,648 |
| C＋S：混合方案 | 3,788,391,368 |
| A：全部保留记录逐条输入 | 25,217,680,296 |

混合方案占比 **15.02%**，指定口径的输入量减少 **84.98%**。四类记录精确对账：程序提取11,840,748条、主体信息1,946,147条、原语义通道392,154条、后备语义通道633,763条，合计14,812,812条。全部2,224个相关文件均完成计数。

## 可复现的计量方法

`scripts/measure_token_routing.py`只读取私有固定批次的文件卡片、原始记录和上下文，使用本地Qwen3-8B tokenizer。它不加载模型权重，不请求推理服务，不改写原批次。

- 使用完整原生解析台账`02_profiles/all_profiles_native.json`确定活动处理单元，与实际字段方案逐一对应。较早的`file_cards.jsonl`缺少13个目标单元，不用于本次计量。
- C使用保存的首次字段方案请求`request.messages`，按Qwen聊天模板计数；包括系统提示、业务定义、文件卡片与样本。一个单元计一次，不把成功回复数量当作卡片数量。
- A和S使用同一单记录模板：system消息为`extract.md`，第一条user消息为文件上下文和事件定义，第二条user消息为一条完整记录，包含记录编号、工作表、行号、完整字段和原上下文；附Qwen生成提示并关闭思考模式。不截断原文。
- 通过聊天特殊标记边界拆开固定上下文和变动记录：固定部分只需分词一次，但每条记录仍计入完整的固定提示token。对分段与完整编码进行一致性校验，避免把可缓存的计数计算误当成可省去的模型输入。
- 逐记录统计四类输入，S只累加row_llm和review，A累加四类。完全重复的来源仍各计一次，本比较不使用内容去重比例。
- 1,048,465条已核实占位行沿用质量剔除；其余记录总数必须精确对账为14,812,812。私有文件级计数、读取文件哈希与脚本哈希保留；公开页仅接收白名单汇总。

`scripts/build_token_comparison.py`校验分流数量和token加法关系，生成`showcase/assets/token-comparison.json`。06卡片、工程处理设计首项及README预览使用同一份汇总。

## 适用范围

这是指定两路、固定单条模板下的**输入量比较**。共同的文件筛选、复杂单元的前置字段规划、输出生成、重试、拆批、超长记录重叠及实际缓存命中不在此式内。全链路用量需要另汇总每次真实请求；GPU耗时、输出成本和语义准确率不能由输入量比例推导。

较早以`1 − 392,154 / 14,812,812`得到的97.35%只表示记录分流，已由token口径替换。工程处理设计中原来的0.97%仍是另一项真实的同表完整内容重复率，但不再用于这块输入量比较。
