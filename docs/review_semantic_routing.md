# 待复核方案转入复杂语义通道

2026-11-25：已修改代码和展示，尚未在真实语料上执行。已完成批次的结果、公开汇总和质量更正版本保持原样。

## 新的处理方式

原批次有475个`mode=review`的独立处理单元，表示字段方案未能可靠确定。新的完整读取逻辑将它们所有可读取的记录加入复杂语义队列，沿用完整记录分块、预算检查、本地LLM抽取、来源核验和结果分流。原有382个`row_llm`单元加上这475个，计划进入该通道的单元共857个；这是计划数量，尚无新执行后的记录数和结果统计。

历史方案原文仍为`review`，不篡改旧判定。`bulk_rows.py`应用新策略`review-plan-to-record-semantics-v1`时改为排队，并保留问题关联。缺失方案以`missing_field_plan`登记并进入同样的后备通道。已经明确排除的单元仍执行排除；字段规则执行过程中产生的其他记录级复核不在这次475个单元的变更范围。

## 问题与来源记录

下次执行时生成：

| 文件 | 内容 |
| --- | --- |
| `06_validation/<file_id>/review_routing_issues.jsonl` | 按处理单元记录原方案原因、模型／校验错误、质量标记、方案版本、卡片哈希、文件及作用域编号、转入策略与稳定`issue_id`。读取失败前也保存。 |
| `06_validation/review_routing_issues.jsonl` | 本次输入范围内各文件问题台账的合并索引。 |
| `06_validation/<file_id>/pending_llm.jsonl` | 每条可读取记录的位置、原值偏移、转入原因及`routing_issue_id`。 |
| `06_validation/mapping_summary.json` | 实际成功读取并转入的记录数、处理单元数及策略版本。 |
| `06_validation/<file_id>/record_results.jsonl` | 模型核验结果和`routing_issue_id`，可回查原方案问题；原文继续在`05_records`留存。 |

问题台账的`execution_status=awaiting_readable_records`表示路由时的登记状态，不代表已完成推理；执行状态与最终结果以队列、汇总和逐条结果为准。转入原因和最终核验错误分别保存，不用成功结果覆盖原问题。

无法读取的文件继续登记`mapping_failure.json`。模型仍无法可靠判断的记录保留`REVIEW`，不会因进入语义通道就自动变成已确认事实。现有`review`结果还包含其他来源的记录级问题，不能将全部复核结果理解为这475个单元。

## 执行边界

当前只发布页面、代码与文档，运行测试仅使用合成小样本，不调用真实模型。没有启动全量流程，也没有改写原有工作目录、模型检查点、问题明细或公开计数。

后续获得执行指令后，应使用独立结果版本，保留现有占位行质量剔除决策；对受影响记录重新抽取、核验、关联及导出，再核对新增队列覆盖、每条记录唯一去向和旧新差异。新增语义请求数量与去重后代表数届时按真实执行统计。
